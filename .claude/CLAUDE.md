# このプロジェクトの共通ルール

## 返答

- 必ず日本語で返事をする。

## プロジェクトの構成

- **ドキュメント**: `docs/`（区分ごとの設計は `docs/db/`）
- **移行ツール**: `migrator/`（暫定対応は `fixups/`）
- **移行ツールの単体テスト**: `tests/`

関係するシステム:

- 旧システム **learningware-kiracari**（MySQL :3306。ステージングは `tenant_id = 10`）
- 新システム **school-launcher**（別リポジトリ。MySQL :3307）

## 作業の進め方

- ドキュメントを変えるときは、旧システム（learningware-kiracari）と新システム（school-launcher）の状況を確認してから行う。
- 移行ツールは、ドキュメントを元に作る。
- 移行ツールを作るときは、合わせて単体テストも作る。
- ドキュメント・移行ツール・migration の3つをずらさない。
  - 移行ツールが前提にするスキーマ（`migrator/steps/schema.py`）と、school-launcher の migration を合わせる。
  - 文書の件数・記述を、実装と合わせる。

## 確認を取ること・してはいけないこと

- school-launcher の migration を実施する（作る・当てる）ときは、事前に確認を取る。
- school-launcher のリポジトリには、migration 以外の変更も事前に確認を取る。新システムのアプリは直さない。
- ブランチの作成・切り替えは、事前に相談する（一時的なものも含む）。
- コミット・push・PR の作成・編集は、指示があるまで行わない。

## データ移行の共通ルール

- 基本的に、すべてのデータを移行する。
- 移行しないのは、次の場合だけ。
  - 移行対象外
  - 親データが存在しない子データ
  - 旧システムと新システムで DB 制約が衝突する場合
- 移さない行は、黙って落とさない。
  - 理由を付けて `out/not-migrated.csv` に出す。
  - 文書の「移さないもの」に件数を書く。
- 削除済みの行も移す。
  - `deleted_at` に削除した日時を入れる。
  - 旧の編集履歴で積まれた重複は、旧の形のまま `*_history` に入れる。
- 値を作り替えない。データの直しは `fixups` で行う。
- 「使われていない」を、移さない根拠にしない。移すかどうかと件数は、ステージングの実データで確かめる。

## 秘密情報

- 平文のパスワードと DB の接続情報は、読まない・移さない（`migrator/db/guards.py` で止めている）。
- `.env`・`overrides*.csv`（個人情報を含む）はコミットしない。
- 接続情報を出力に表示しない。

## 動作確認

### 観点

- データが正しく移行できているかを見る（欠落・取り違え・重複・制約違反・旧との不一致）。
- 新アプリの画面や編集の不具合は対象外。
- 旧 DB は読むだけにする（書き込まない）。

### 単体テスト

移行ツールを変えたら、単体テストを流す。

```bash
.venv/bin/python -m unittest discover -s tests
```

### 移行の確認

school-launcher の今の migration を当てた、空の DB で行う。

1. `doctor` で、必須のスキーマがそろっていることを確かめる。
2. `run` を流す。
3. `verify` で、突き合わせの差分が 0 で、旧 DB との照合がすべて一致することを確かめる。
4. 同じ内容で流し直し（`run --phase foundation.2 --section content --section enrollment --section billing --section support`）、投入が 0 件であることを確かめる。
5. `out/not-migrated.csv` の理由ごとの件数が、文書の「移さないもの」と合うことを確かめる。

空の DB の扱い:

- 確認用の別名の DB で行う（例: `lw2_schema_check`）。確認が終わったら消す。
- ローカルの `learningware` を作り直す（`make reseed` など）ときは、事前に確認を取る。
- 8080 番を旧システムが使っているときは、`BTOC_BACKEND_PORT=18080` を付けて作り直す。

### 移行にかかった時間の記録

区分ごとに、移行にかかった時間を計測して記録する。

- **計測**
  - `run` の出力をログに残す。
  - 区分（common / foundation / content / enrollment / billing / support）ごとの時間は、各フェーズの見出し（`=== foundation.1 … ===`）の時刻の差から出す。
  - 合計の時間と、流し直しの時間も出す。
- **記録**: [`docs/migration-timing.md`](../docs/migration-timing.md) に、1回の確認を1行で追記する。
  - 日付
  - 移行ツールのコミット
  - school-launcher の最後の migration
  - 移行元
  - 区分ごとの時間と件数
  - 合計
  - 流し直しの時間
- 前回より大きく遅くなった区分があれば、報告で触れる。

### 報告

- 確かめたことと、確かめていないことを分けて報告する。
- 失敗は、そのまま報告する。
