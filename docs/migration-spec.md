## 1. 区分をまたぐ登録順

新環境は**実 FK を持つ**ため順序が強制される。**前のフェーズが終わるまで次に進まない。**

```
フェーズ0  新環境のスキーマ追加（各区分の review.md の追加一覧）
              ↓
フェーズ1  基盤 — テナント → マスタ → 会員 → 会員に紐づくもの
              ↓  ここが終わるまで他区分は1行も入らない
フェーズ2  オンデマンド（講座・レッスン）／ 運営（お知らせ・問い合わせ）
              ↓  courses.instructor_id は NOT NULL。講師の users 行が先
フェーズ3  ライブ ／ 受講 ／ 課金
              ↓  受講と課金は講座に依存する
フェーズ4  就職支援（別 DB: career）
```

> **フェーズ2以降の詳細は未確定。** 各区分の突き合わせに `修正方法` の列が無く、区分内の順序が決まっていない。

**ツールでの指定は `区分.フェーズ番号`。** ここに書いた区分の順序と、各区分の `migration-spec.md` 2章に書いた区分の中の順序は**別の軸**なので、1つの通し番号にまとめない（区分が増えると番号がずれる）。

```bash
python -m migrator plan                          # 区分とフェーズの一覧
python -m migrator run --section foundation      # 区分まるごと
python -m migrator run --phase foundation.4      # 区分の中の1フェーズ
```

**共通の根拠**

- `tenants` が無いと `tenant_id` を持つ全テーブルが FK 違反になる
- マスタ（`*_statuses` / `*_kinds` / `*_methods` / `user_roles`）は FK の参照先なので、値を使う行より先
- **就職支援は別 DB（career）**。DB をまたぐ FK は張れないので、`user_id` は ULID の値としてだけ持ち、整合は ETL 側で保証する

## 2. 処理の段

`extract`（抽出）→ `transform`（変換）→ `load`（投入）の3段。各段を個別にも実行できる（[README](../README.md)）。

| 段 | 入力 | 出力 | 責務 |
|---|---|---|---|
| extract | lw2 (MySQL) | 中間ファイル | `tenant_id = 12` に絞って読み出す。**禁止列を SELECT しない** |
| transform | 中間ファイル | 変換済みデータ | 型・コード値・タイムゾーン・極性の変換、ULID 採番 |
| load | 変換済みデータ | school-launcher (MySQL) | FK 順に投入。冪等に再実行できること |

## 3. 全区分に共通する規則

### 3.1 テナントの絞り込み

- lw2 は**同一 DB に73テナントが同居**している。すべてのクエリに `tenant_id = 12` を入れる
- **`tenant_id` 列を持たないテーブルがある**（`enquete_answer` など）。親テーブルと join して絞る。**join を落とすと最大 2,083 倍の行を拾う**（ETL設計 付録A）
- `tenant_id` を持たない共通マスタ（`role_master` / `profile_cate` など）は全行読み、移すときに recademy 用として扱う

### 3.2 ID の採番

- 旧 `int(11)` auto_increment → 新 `char(26)` ULID（26文字の Crockford Base32。先頭10文字が生成時刻48bit、残り16文字がランダム部80bit）
- **`tenants.id` は基盤フェーズで採番した1値を設定値として配る。** 再計算しない
- 他テーブルは**決定論 ULID**（旧テーブル名 + 旧 PK から再現できる採番）。再実行しても同じ ID になるため二重登録を防げる
- **新環境の既存コードは `ulid.Make()`（ランダム）しか使っていない。** 既存行との突き合わせは ULID ではなく業務キー（`tenants.slug`、`external_user_links.external_id`）で行う
- **`access_log` と `test_sub_question` は旧 ID を外部キーとして引き継げない**（採番の枯渇・履歴断裂）

### 3.3 日時とタイムゾーン

- 旧は全584列が `datetime`（JST naive）。新は `timestamp` 397 / `datetime(3)` 174 / `datetime` 26 / `timestamp(3)` 2 が**同じテーブル内でも混在する**
- **`timestamp` 列はセッション TZ で UTC 変換される**ので、JST naive をそのまま書くとずれる。**`datetime(3)` 列は変換されない**ので UTC に直した値を明示的に書く
- → **列ごとに型を引いて分岐する仕組みを基盤に入れる。テーブル単位で決め打ちすると必ず事故る**
- `date` → 日時型は**日付境界で1日ずれる**（JST 00:00 → UTC 前日15:00）。開始日か終了日かで 00:00:00 / 23:59:59 を補う

### 3.4 文字コード

- 旧 `utf8`(utf8mb3) / `utf8_unicode_ci` → 新 `utf8mb4` / `utf8mb4_unicode_ci`。拡大方向なので基本は安全
- **cp932 混入の可能性がある**（`test` テーブルのカラムコメントが文字化けしている）。**抽出時に文字コード検証を入れる**

### 3.5 桁と NULL

- `varchar` の縮小がある箇所は**抽出時に超過件数を検査**し、0件でなければ**列を広げる**（切り捨てない）
- 新の NOT NULL 列に入れる値が旧に無い場合は、**既定値で埋めず、何を入れるかを運営判断にする**

### 3.5.1 NOT NULL / UNIQUE / 外部キーに当たる行

**全区分で同じ扱いにする。区分ごとの確認事項にしない。**

1. **移さない。** 変換した直後に移行先のスキーマ（`information_schema`）と突き合わせ、
   当たった行は投入しない（`migrator/validation/constraints.py`）
2. **値を作り替えない。** 合成した値で通すと、**どれが本物か分からなくなる**。
   ツールは「誰が・なぜ入らないか」を `work_dir/not-migrated.csv` に出すだけ
3. **UNIQUE が重複したら、その組はどれも移さない。** どれを残すかはツールが決めない
   （決めた時点で暫定対応になる）
4. **直すのは移行の外**（暫定対応ツール `fixups`）。移行元を直す SQL か、
   運営が値を決める補正データ（`overrides.csv`）として当て、**そのあと同じコマンドで再実行**すれば入る
5. **外部キーは2種類ある。区別して扱う。**
   - **巻き添え** — 親は移行元にあるが、親自身が制約に当たって移らなかった場合。
     **大本を直せば消える**ので、子を個別に直さない（会員が1人移らないと、その会員の
     住所・通知設定・所属も移らない）
   - **親が存在しない子データ（孤児）** — 移行元の時点で親の行が無い場合。
     旧環境で親だけ物理削除され、子が取り残されたもの。**復元できないので移さない。**
     移行元から消すかどうかは暫定対応の判断で、**区分の確認事項にしない**
     （消しても移行結果は同じ。消さなければ毎回一覧に出続ける）

> **区分の確認事項に書くのは「どう直すか」ではなく「直せない事情があるか」だけ。**
> 欠損・重複そのものは**この規則で機械的に処理される**ので、確認事項にはしない。
> ただし**規模が大きいものは注意事項として記録する**（何割の会員が止まるかは移行計画に効く）。

### 3.6 フラグ・コード値

- **極性が反転する変換が複数ある**（「受け取る」→「optout（受け取らない）」、「削除フラグ」→「有効フラグ」）。取り違えると通知が真逆に出る
- コード値（`role_id` / `pref_id` / 各種 `*_type`）は**対応表を作り、対応表に無い値が来たら停止する**
- **`platform_admin` は絶対に出力しない**（付くと他テナントが見える）

### 3.7 冪等性とエラー処理

- 同じ入力で再実行しても二重登録にならないこと。**決定論 ULID と業務キーの UNIQUE** で担保する
- **UNIQUE 違反で止まることを冪等性の担保にしない**（キーを変えれば通ってしまう）。投入前に存在確認する
- 途中で失敗したら**フェーズ単位でやり直せる**こと。部分投入のまま次へ進まない
- **`--dry-run`** で件数と変換結果を確認してから本番投入する

### 3.8 移行の対象外

**2種類ある。** 区分ごとの一覧は各 `migration-spec.md` の「移行の対象外」にある。

**A. 移行できないもの** — 移そうとしても成立しないもの。

- **新環境では使えない値** — 旧環境の DB 接続情報、旧アプリのシークレット。**移しても指す先が違って機能しない**。新環境では登録し直す（シークレットは**再発行が原則**）
- **移した時点で無効な値** — 発行中のトークン・認証コード。有効期限つきの一時値
- **持ち出してはいけない値** — 平文のパスワード・シークレット・認証コード。**「移さない」ではなく「読み出さない」**。抽出 → 中間ファイル → 再投入という経路に乗せること自体が漏洩面を増やすため、**抽出クエリで SELECT しないことをレビューで確認する**
- **対応する概念が無い値** — 入れる先が無いのではなく、入れても参照されない

**B. 方針として移行しないもの** — 対象外区分のデータ、純ログ、UI の一時状態、都度計算できる集計、運営の判断で対象外にしたもの。

> **「受け皿が無い」「新環境に機能が無い」は対象外の理由にならない。** それらは受け皿を追加して移す。

## 4. 全区分に共通する検証

| 検証 | 方法 |
|---|---|
| 対象テナントが1件か | `SELECT id, name FROM tenants WHERE slug = '<slug>'`。**総数では判断しない**（デモ seed のテナントが同居しているのが正常） |
| 件数の照合 | 抽出時に記録した件数と投入後の件数を突き合わせる |
| `platform_admin` が0件か | 1件でもあれば停止して原因を追う |
| 日時のずれ | `timestamp` 列と `datetime(3)` 列をサンプリングし、JST に戻して元の値と一致するか確認する |
| 文字化け | cp932 混入が疑われる列をサンプリング |
