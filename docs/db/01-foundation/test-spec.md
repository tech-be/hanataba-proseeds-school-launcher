移行の見直しの手順 2（[進捗](../rework-progress.md)）。[機能仕様書](functional-spec.md)をもとに、**移したデータで新システムの機能が正しく使えるか**を確かめるテストケースを並べたもの。

- **移行元**: ステージング `tenant_id = 10`

## 8. 新システムに機能が無いもの（テストしない）

次は、移しても新システムの動きに効かない（[機能仕様 0](functional-spec.md#0-新システムが使っていない表列)）。**テストはしない。** 移すかどうか・どう残すかは手順 3 で決める。

- ログインできる時間帯（`tenant_login_windows`）、SSO の設定、SNS ログイン（Facebook / X / Instagram）のシークレット
- 会員数の上限（`tenant_limits`）、登録時の既定値（`tenant_field_defaults`）、公開範囲（`user_field_visibility`）
- 講師の担当範囲（`instructor_assignments`）、グループの階層・グループ管理者による絞り込み
- テナントの略称・既定の言語、`settings` の `service` / `features` / `lw2_*`
- 会員の姓・名（別の列）、携帯の電話・メール、言語、自己紹介、血液型、運営メモ、ログインの記録

## 9. E2E の環境（2026-10-26 決定）

| 項目 | 案 |

## 10. 実装の方針（データの確認）

- データの確認（D）は、`verify` に組み込む。今の `migrator/validation/legacy_checks.py`（旧 DB と移行先を SQL で直接比べる）とは別に、**新アプリの問い合わせ条件を写したテスト**として `migrator/validation/spec_checks.py`（新規）に、ケース ID（F-10 など）ごとに持つ。`verify` の結果に ID を出す。
- E2E（E）は、ケース ID をテストの名前に入れる。
