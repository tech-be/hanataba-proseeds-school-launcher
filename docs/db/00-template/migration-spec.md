# ＜区分名＞ — 移行仕様

> **これはひな形です。** `00-template/` ごと `NN-<区分名>/` にコピーし、[breakdown.md](breakdown.md) / [review.md](review.md) と3点セットで使ってください。**このディレクトリは区分ではないので、README の区分一覧にも集計にも含めません。**

＜この区分で移すものを1〜2行。旧何件 → 新何件、ETL が実際に書き込むテーブル＞

- **根拠**: 旧⇔新の判断は [review.md](review.md)。**本書はそれを実装の手順に落としたもの**で、個別カラムの判断は突き合わせを正とする
- **全区分に共通する規則**（抽出の絞り込み / ULID / 日時 / 文字コード / 冪等性）は [移行ツール仕様書](../../migration-spec.md) にある。**ここには書かず、区分固有のことだけを書く**
- **[移行の原則](../00-template/review.md#移行の原則)** に従う。対象外区分のデータ以外はすべて移し、受け皿が無ければ追加し、元の構造を維持する
- 新環境に足す DDL は [schema-additions.md](schema-additions.md)（**足すものがある区分だけ**作る）

> ＜この区分の前提を1〜2行。何が先に入っている必要があるか、他区分への依存＞

## 1. データ登録前確認事項（運営判断）

**着手前に閉じるもの。** 未確定のまま流すと、作り直しか誤データになる。

### 1-1. 決定が要るもの

**[review.md](review.md) の `未決:` と、追加一覧に挙げた判断を漏れなく載せる。** 件数が合わないときはどちらかが古い。

> **機能の有無・運用の有無は移行の可否に関係しない。** 「新環境にその機能が無い」「もう使っていないかもしれない」は確認事項にならず、**データは移す**（[移行の原則](../00-template/review.md#移行の原則)の1）。機能を作るかどうかは移行とは別の判断なので、**追加一覧の「変更が必要な機能」に書き、ここには書かない。**

| # | 確認事項 | 閉じないと何が起きるか | 根拠 |
|---:|---|---|---|
| 1 | **＜運営が決めること。「〜してよいか」「〜をどうするか」の形＞** | ＜投入が止まる / 誤データになる / 後から直せない、のどれか＞ | [＜節＞](review.md#＜アンカー＞) |

> **書き方**: 「確認事項」は**運営が YES/NO か選択肢で答えられる粒度**にする。実装側の検討事項（どう作るか）はここではなく3章に書く。
>
> **対象で小見出しに分ける**（テナント / 会員 / 定義データ / セキュリティ など）。運営が答える単位で並べたほうが早く閉じる。
>
> **ここに載るのは主に次の3つ。** ①移行対象の範囲（どのテナント・どの会員まで）②**対応表が要るもの**（旧コード値 → 新コード値、旧 ID → 新 slug）③セキュリティ上の承認。
>
> **NOT NULL / UNIQUE / 外部キーに当たる行は確認事項にしない**（**親が存在しない子データ**も含む）。 扱いは[共通仕様 3.5.1](../../migration-spec.md#351-not-null--unique--外部キーに当たる行)で決まっている（**移さず一覧に出し、暫定対応で直してから再実行する**）。区分ごとに決め直さない。**規模が大きいものだけ [1-4 注意事項](#1-4-注意事項共通仕様で扱うもの)に記録する。**

### 1-2. 決定済み（再確認だけ）

＜すでに合意が取れているもの。後から蒸し返さないために残す＞

| 事項 | 決定 |
|---|---|
| ＜項目＞ | **＜決定内容＞** |

### 1-3. 本番ダンプ受領後に確認すること

＜スキーマからは判断できず、実データを見ないと決まらないもの。[README](../README.md) の「実データが無いと判断できないこと」と重複してよい＞

| 確認 | 効く先 |
|---|---|
| ＜どの値を見るか＞ | ＜その結果が何を決めるか＞ |


### 1-4. 注意事項（共通仕様で扱うもの）

**判断は要らないが、規模を知らせておくもの。** [共通仕様 3.5.1](../../migration-spec.md#351-not-null--unique--外部キーに当たる行) の規則で
機械的に処理されるため確認事項にはしないが、**何割が止まるかは移行計画に効く**ので数字を残す。

| 対象 | 実測 | 共通仕様での扱い |
|---|---:|---|
| `＜旧テーブル.列＞` が ＜NOT NULL / UNIQUE＞ に当たる | ＜件数＞ | ＜移さない。暫定対応で何を決めるか1行＞ |

> ＜無ければ「なし」と書く＞

## 2. データ登録順

＜新環境は実 FK を持つため順序が強制される。**前のフェーズが終わるまで次に進まない**＞

```
フェーズ0  ＜新環境のスキーマ追加が要るならここ。DDL は schema-additions.md＞
              ↓
フェーズ1  ＜マスタ / 定義系。FK の参照先になるもの＞
              ↓
フェーズ2  ＜親データ＞
              ↓
フェーズ3  ＜子データ。親の行が揃ってから＞
```

**順序の根拠**

- ＜なぜその順でなければならないかを FK 名や NOT NULL 制約で示す。「先に入れないと FK 違反」だけでなく、**どの列がどのテーブルを指しているか**まで書く＞
- ＜他区分に依存する箇所があれば、どの区分のどのフェーズの後かを明記する＞

## 3. データ移行仕様

### 3.1 抽出（extract）

**この区分固有の絞り込み**

- ＜`tenant_id` を持たないテーブルがあれば、どの親と join して絞るか＞
- ＜除外する行があれば条件と理由（見出しブロック、削除済み、テスト用など）＞

**SELECT してはいけない列**

＜平文の認証情報など。無ければ「なし」と書く＞

| テーブル | 列 | 理由 |
|---|---|---|
| `＜テーブル＞` | `＜列＞` | ＜平文の認証情報 など＞ |

**事前検査**

| 検査 | 対象 | 判断 |
|---|---|---|
| ＜桁溢れ / NULL / 重複 / コード値の網羅＞ | `＜テーブル.列＞` | ＜0件なら続行、あれば何を決めるか＞ |

### 3.2 変換（transform）

**この区分のテーブル別仕様は [review.md](review.md) が正。** ここには**複数テーブルに共通して効く規則**と、**取り違えると致命的なもの**だけを書く。

| 変換 | 規則 |
|---|---|
| `＜旧列＞` → `＜新列＞` | ＜コード値の対応 / 単位換算 / 極性の反転 / 分解・展開＞ |

> **取り違え注意。** ＜意味が変わるもの（`del_chk` を「中止」に写す、フラグの極性が逆、単位が月と日で違う 等）を名指しで書く＞

### 3.3 投入（load）

- **冪等性**: ＜何で担保するか。決定論 ULID / 業務キーの UNIQUE / 投入前の存在確認＞
- **投入前の確認**: ＜重複を防ぐために先に引くクエリがあれば＞
- **エラー時**: ＜どの単位でやり直せるか＞

### 3.4 移行の対象外

＜[移行の原則](../00-template/review.md#移行の原則)の1の例外だけ。無ければ「なし」と書く。**理由の性質で2つに分ける**＞

**A. 移行できないもの** — 移そうとしても成立しない。

| 対象 | なぜ移行できないか |
|---|---|
| `＜テーブル.列＞` | ＜新環境では使えない値 / 移した時点で無効な値 / 持ち出してはいけない値 / 対応する概念が無い のどれか。**なぜ成立しないかを具体的に**＞ |

> ＜平文の認証情報がある場合は「移さない」ではなく**「読み出さない」**と書き、抽出クエリのレビュー項目にする＞

**B. 方針として移行しないもの**

| 対象 | 理由 |
|---|---|
| `＜テーブル＞` | ＜対象外区分 / 純ログ / UI の一時状態 / 都度計算できる集計 / 運営の判断（誰がいつ決めたか）＞ |

### 3.5 検証

**投入後に必ず通す。**

| 検証 | 方法 |
|---|---|
| 件数の照合 | ＜抽出時の件数と投入後の件数＞ |
| ＜この区分特有の検証＞ | ＜クエリか手順。運営に見てもらうものはその旨＞ |
