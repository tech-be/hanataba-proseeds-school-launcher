# ＜区分名＞ — 突き合わせ

> **これはひな形です。** `00-template/` ごと `NN-<区分名>/` にコピーし、[breakdown.md](breakdown.md) / [migration-spec.md](migration-spec.md) と3点セットで使ってください。**このディレクトリは区分ではないので、README の区分一覧にも深刻度の集計にも含めません。**

[＜区分名＞の内訳](breakdown.md) の対応表と **1対1で対応させる**。内訳の行1つにつき、この文書に `###` 見出しを1つ置く。**順序も内訳と揃える。**

- **片方だけを更新しない。** テーブルの割り当てを変えたら内訳と突き合わせの両方を直す
- 観点（テーブル / カラム / 型 / 性質）と深刻度（高 / 中 / 低）の定義は [README.md](../README.md#突き合わせの4つの観点) を参照
- **「内容」は問題点だけ、「修正方法」はどう直すかだけ**を書き、同じことを二度書かない。修正方法は動詞で始め、**誰が何をすれば閉じるか**が分かる粒度にする
- ローカルデータ数と A·B·C の定義は [README.md](../README.md#共通の列の意味) を参照。**値は内訳と一致させる**

## 移行の原則

**この4つが判断の前提。** 個別の行で迷ったらここに戻る。

### 1. 対象外に区分されたデータ以外は、すべて移行する

**「新環境にその機能が無い」は移行しない理由にならない。** 機能の有無とデータの移行は別の話で、**データは移し、機能は別途用意する**。同じく**「もう使っていないかもしれない」も理由にならない**。

移行の対象外にできるのは次の2種類だけ。**どちらも「例外: 」で始め、理由を必ず書く。**

**A. 移行できないもの**（移そうとしても成立しない）

| 型 | 理由の書き方 |
|---|---|
| **新環境では使えない値** | 旧環境の接続情報・旧アプリのシークレットなど。**移しても指す先が違って機能しない**ことを書く |
| **移した時点で無効な値** | 発行中のトークン・認証コード。**有効期限つきの一時値**であることを書く |
| **持ち出してはいけない値** | 平文のパスワード・シークレット・認証コード。**抽出 → 中間ファイル → 再投入という経路に乗せること自体が漏洩面を増やす**。「移さない」ではなく**「読み出さない」**と書き、抽出クエリのレビュー項目にする |
| **対応する概念が無い** | 入れる先が無いのではなく、**入れても参照されない**ことを書く |

**B. 方針として移行しないもの**（移せるが移さないと決めたもの）

| 型 | 理由の書き方 |
|---|---|
| **対象外（未コミット）に区分されたデータ** | どのデータ種で対象外になったかを書く |
| **純ログ**（棚卸しの A 区分） | **名前で判断しない** — `user_login_chk_log` は「ログイン有効期間の変更履歴」、`user_learning_unit_log` は「学習実績の本体」で、いずれも `_log` という名前だがログではないので移行する |
| **UI の一時状態 / 都度計算できる集計** | 作り直せる・計算できることを書く |
| **運営の判断で対象外** | **誰がいつ決めたか**が分かるように書く（例: プロフィール画像） |

> **「受け皿が無い」「新環境に機能が無い」「使っていないかもしれない」はどれも理由にならない。** それらは原則2の追加対象。

### 2. テーブル・カラムが足りなければ追加する

受け皿が無いことは「落とす」理由ではなく、**新環境に追加する作業**になる。追加するときは次の3つをセットで書く。

- **追加案**（テーブル名・列名・型。旧環境の構造を参考にする）
- **旧環境の対応**（どの列から来るのか）
- **変更が必要な機能**（DDL を足すだけでは動かない。構造体 / repository / DTO / 画面のうち、**決めが要るところ**を列挙する）

書き方は [基盤の追加一覧](../01-foundation/review.md#新環境に追加するテーブルカラム) を参照。

**ここで決めた追加を migration の単位に落としたものが [schema-additions.md](schema-additions.md)。** DDL・適用順・ロールバックの注意はそちらに書く。

### 3. 元の構造を維持する

**旧の1列は新の1列に、旧の1テーブルは新の1テーブルに対応させるのが既定。** 次はいずれも**情報が落ちる**ので、勝手にやらない。

- **複数列を1列に畳む**（`tel` と `mobile_tel` を `phone` に、`valid_chk` と `del_chk` を `status` に）
- **列やテーブルを削る**（「使っていなさそう」「新環境に無い」を理由にしない）
- **粒度を変える**（2組ある住所を1組にする、履歴テーブルを最新1行に丸める）

### 4. 新環境の構造に合わせる場合は確認する

新の作り（ルックアップ表・ULID 主キー・`tenant_id` 必須）に寄せるのが妥当な場面もある。その場合は**合わせる理由と、それで何が表現できなくなるかを書いたうえで確認を取る**。無断で統合・削除しない。

> 例: `birth_date`（date 1列）を `birth_year` / `birth_month` / `birth_day` の3列に分けるのは、新環境が「生年は必須・生月日は任意」を設定できる仕様に合わせたもの。**合わせる理由と失うもの（単一の日付として扱えない）を書いて確認する。**

## ＜中分類ID＞ ＜中分類名＞

内訳: [breakdown.md](breakdown.md) の同名の節

エントリは次の4形のどれかになる。内訳の行の形（旧のみ / 新のみ / 両方）で決まる。

### 形1 — 両方あり・指摘あり

```markdown
### `＜旧テーブル＞` → `＜新テーブル＞`

`＜旧＞` (N列) → `＜新＞` (M列) ／ ETL段 ＜L0〜L9 または —＞ ／ ローカルデータ数 ＜n＞ / ＜A|B|C＞

そのまま対応: ＜n＞列

| 旧カラム | 新カラム | 観点 | 深刻度 | 内容 | 修正方法 |
|---|---|---|:--:|---|---|
| `＜旧カラム＞` ＜型＞ | `＜新カラム＞` ＜型＞ | ＜観点＞ | ＜深刻度＞ | ＜何が起きるか。根拠（docs/db の行 / migration の DDL / ETL設計の節番号）を必ず引く＞ | ＜どう直すか。動詞で始める＞ |

**まとめ**: 受け皿が無い列 ＜n＞ / 変換規則が要る列 ＜n＞ / 高 ＜n＞ 件
```

### 修正方法の書き方

**動詞で始め、その1件を閉じるのに必要な行動を1つ書く。** 型は次のどれかに寄る。

| 型 | 書き出しの例 |
|---|---|
| ETL の変換規則 | `ETL で …に変換する` / `…を除外して抽出する` |
| **受け皿の追加** | `` `＜テーブル＞.＜列＞` を追加して移す（→ 追加一覧 Ax）`` ／ `` `＜テーブル＞` を新設して移す `` |
| migration の追加 | `migration で `＜テーブル＞` に …を足す` |
| 運営・関係者への確認 | `運営に…を確認する` / `…の方針を決める` |
| 実データでの確認 | `抽出時に…を検査する`（[README.md](../README.md) の「実データが無いと判断できないこと」に載せる） |
| **構造を変える判断** | `＜合わせる理由＞のため…に寄せる。＜失うもの＞を運営に確認する` |
| **例外（移行しない）** | `**例外: 移行しない。** ＜なぜ移すこと自体が不適切か＞` |
| 受け入れる | `対応不要。＜なぜ許容できるか＞` |

> **「移行しない」は原則1の例外だけ。** 受け皿が無いことを理由にする書き方（`受け皿が無いので移行しない`）は**使わない** — それは原則2の追加対象になる。

**まだ決まっていないものは「未決:」で始める。** 例: `未決: 会員に見せていた番号かを運用に確認し、移行先を作るか決める`。未決のまま残っている件数が、そのまま実装前に閉じるべき論点の数になる。

### 形2 — 旧のみ（新に受け皿なし）

```markdown
### `＜旧テーブル＞` → なし

`＜旧＞` (N列) ／ ローカルデータ数 ＜n＞ / ＜A|B|C＞

**該当テーブルなし。** ＜何のテーブルで、受け皿が無いと何が起きるかを1〜2行＞

| 旧カラム | 観点 | 深刻度 | 内容 | 修正方法 |
|---|---|:--:|---|---|
| `＜旧カラム＞` ＜型＞ | ＜観点＞ | ＜深刻度＞ | ＜問題点＞ | ＜追加するもの。原則2＞ |

**まとめ**: 受け皿が無い列 ＜n＞ / 高 ＜n＞ 件
```

**受け皿が無い＝落とす、ではない。** 原則1・2により、既定は**新環境に追加して移す**。追加するものと変更が必要な機能を区分末尾の追加一覧にまとめ、各行からそこへ参照を張る。

### 形3 — 新のみ（旧に対応なし）

```markdown
### なし → `＜新テーブル＞`

`＜新＞` (M列, ＜データ|マスタ|中間|イベント・履歴|設定＞)

**旧に対応テーブルなし。** ＜migration で投入する / 運用で登録する / 新規機能 のどれかと、その理由を1〜2行＞
```

指摘がある場合（移行時に値を作る必要がある等）は形1と同じ表を付ける。

### 形4 — 指摘なし

```markdown
### `＜旧テーブル＞` → `＜新テーブル＞`

`＜旧＞` (N列) → `＜新＞` (M列) ／ ETL段 ＜Lx＞ ／ ローカルデータ数 ＜n＞ / ＜A|B|C＞

**問題なし。**
```

**「問題なし」と書けるのは指摘が1件も無いときだけ。** 深刻度「低」だけでも指摘があれば表に残す。

## 新環境に追加するテーブル・カラム

＜原則2で追加すると決めたものを、この区分の分だけ通し番号（A1, A2, …）で並べる。各行から参照する＞

| # | 追加するもの | 旧環境の対応 | 変更が必要な機能 |
|---|---|---|---|
| **A1** | `＜テーブル＞.＜列＞` ＜型＞ ／ `＜新設テーブル＞`（＜主なキーと列＞） | `＜旧テーブル＞.＜旧列＞` | ・＜決めが要る機能を3〜5個＞<br>・＜DDL を足すだけでは動かない箇所＞ |

> **DDL を足すだけでは機能しない。** 構造体 → repository → service → DTO → handler → フロントの型 → 画面の定型部分は省き、**判断が要るところだけ**を書く。

### 移行しない例外

＜原則1の例外。対象外区分のデータと、移すこと自体が不適切なものだけ＞

| 対象 | 理由 |
|---|---|
| `＜テーブル.列＞` | ＜平文の認証情報 / 発行中のトークン / UI の一時状態 / 都度計算できる集計 のどれか＞ |
